# ch16｜保持最新、學會說不、讓事業複利成長（含結論與附錄）

## 這章在講什麼

- 核心問題是客戶最常問的「為什麼不直接用大廠的代理產品？」作者的答法是先講自己的極限：系統已在大廠生態裡、要單一供應商加支援合約與法人時，大廠就是對的；再給客戶三個能在對方現行文件中查證的點（記錄行為與花費、個別代理預算上限、聘用需人類核准）。
- 跟上快速變動的開源專案，用的是「有上限的例行」：每週同一天 30 分鐘，依序讀 release notes、承諾過功能的文件頁、相依性登記表的 issue，一年約 23 小時。產出不是知識，而是把每個變更分進 No effect／Review／Act 三桶；Act 一律變成五分鐘的 release call。
- 說不是一種信用：五種要婉拒的客戶（期待零人力、需要廠商、只要一個代理、沒人坐董事席、需要你不是的專業），每次拒絕都附一個替代方案；早說、白說、一句話給理由。
- 談年輕開源專案的風險只講有日期、有出處的事實，不猜動機；用鎖版本、備份與還原測試、帳號資料歸客戶、每季檢查、一頁退場計畫管理延續性。
- 十二個月的成熟事業不是更大，而是記錄得更好：客戶階梯、技能庫、藍圖組、登記表與發布日誌、實測案例、雙向轉介。技能、藍圖、方法與信任會複利；預設值、狀態筆記、沒日期的數字會衰退。承諾工時連續三個月超過產能 75% 才考慮第二位交付人員。
- 結論〈The Board Seat〉：交出鑰匙很容易，設計座位才是工作——上限、關卡、評分表、章程與節奏，讓一個人能治理代理。附錄 A～F 提供四個藍圖、章程與預算政策範本、建置手冊、discovery call 腳本、定價參考與 90 天啟動計畫。

## 作者做過的實驗／例子

- 開場：顧問第二次拜訪小型物流仲介，創辦人問為何不用大廠產品。顧問先說大廠何時是對的，再寫下三個檢查點；兩週後 IT 外包回報有一項不符合，顧問拿到治理與預算稽核案。
- 發布速度：2026-09-16 到 10-12 四週五次發布，10-20 最新為 v2026.1012.0，分 stable、beta、nightly、canary 通道。
- 風險事實：6 月獨立研究頁記錄化名主導者、資金未揭露、多數合併來自單一帳號、4,953 個開放 issue 與 105 位貢獻者；10 月 repo 約 104,500 顆星、授權頁改列公司名並稱由團隊維護。兩份資料不一致，要照實說出差異。
- 產能：每週 20 小時 × 46 週＝920 小時，約每月 77 小時；一個月費客戶約 12 小時，兩個 31%、四個 63%、六個 94%。
- 定價錨點（附錄 E）：Blueprint and Setup $3,500～7,000、Audit $1,500～3,500、Company Build $6,000～12,000、Retainer 每月 $2,500～7,500；五代理四 connector 兩審查對外產出客戶雲端的 Build 為 $11,200。

## 教練解說要點

- 「跟上版本」的成本要算出來：全讀一年兩百多小時、不讀就讓客戶先發現；固定 30 分鐘把它變成可定價的服務成本。
- 分桶規則的關鍵在「有沒有碰到客戶在用的功能」與「是不是改預設、移除、安全」兩個維度；文件與 staging 行為衝突時相信 staging。
- release call 的五段結構（改了什麼、影不影響、怎麼測、建議、你要做什麼）才是客戶買月費買到的東西，changelog 不是。
- 說不的評分表要在 discovery call 第 18～24 分鐘「默默」跑一次；婉拒要跟替代方案綁在一起才可信。
- 「不像在辯護」可以量：先承認極限、三個檢查點齊全、沒有貶低或保證語氣、150 字以內。

## 演練

> 說明：練習視窗工作目錄是 practice/。本書沒有附程式：用 Python 標準庫（不可 pip 安裝任何套件）寫小模擬，檔案放 practice/ch16/interactive/，用 `PYTHONUTF8=1 python ch16/interactive/xxx.py` 執行。需要真實模型時用 practice/llm_agent.py 的 ask／ask_json（走 claude -p），整章最多呼叫 2 次。

### 練習 1：每週版本追蹤的三桶分類器與 release call

**目的**：把 16.1 的例行變成程式：輸入一串變更，輸出 release log 與給受影響客戶的訊息。
**送給練習視窗的提示詞**：

```text
寫 ch16/interactive/release_triage.py（只用標準庫，不可 input()，30 秒內跑完）：
1. 定義三個客戶各自使用的功能集合（budgets、approvals、routines、backups、skills 擇用）。
2. 定義 8 筆變更：版本、日期、功能、種類（new_feature、bugfix、default_change、removed、security、docs），其中一筆是「文件寫有、staging 沒有」的衝突。
3. 分類：不碰任何客戶在用的功能 → No effect；碰到且種類為 default_change／removed／security → Act；其他 → Review。衝突項動作加註「相信 staging 並記錄」。
4. 寫 ch16/interactive/release_log.csv（一行一筆：版本、日期、桶子、受影響客戶、動作）。
5. 為每個 Act × 受影響客戶產生一則五段訊息（改了什麼／對你的公司影不影響、為什麼／我怎麼測／我建議／你要做什麼），寫進 release_calls.md，並印出每則字數與 changelog 原文長度做對照。
```

**觀察重點**：

- 三個桶子的筆數是否合理，No effect 是否真的不碰任何客戶？
- 每則訊息是否都能回答「這對我的公司代表什麼」，而不是轉貼 changelog？
- 衝突項有沒有被標記，而不是照文件直接寫進客戶訊息？

### 練習 2：說不的評分表＋讓模型回答「為什麼不用大廠」

**目的**：把 16.2 五種不適配與開場三檢查點做成可檢查的流程，並檢查真實模型的回答有沒有在辯護。
**送給練習視窗的提示詞**：

```text
寫 ch16/interactive/fit_and_vendor.py（只用標準庫）：
1. 定義 7 位潛在客戶的訊號（期待零人力、需要廠商合約、需要代理數、董事每週可給時數、是否受監管），依五種不適配類型判定，婉拒者套用「誠實的拒絕」範本並附替代方案，寫進 fit_screen.md。
2. 加月費測試：月費 3000 是否 ≤（月淨值 − 監督成本）× 0.5，不符者改提年度稽核。
3. 用 practice/llm_agent.py 的 ask_json 呼叫 claude -p 一次：請模型以顧問身分用 150 字內回答「為什麼不直接用大廠的代理產品？」，開頭先承認大廠何時是對的，再列三個查證點；輸出 {"answer":..., "vendor_right_when":[...], "three_checks":[...]}。
4. 用程式檢查回答（不再呼叫模型）：字數 ≤150、前半段是否承認大廠適用情境、三個檢查點關鍵字是否齊全、有無辯護或貶低詞（其實、絕對、更好、不安全、被綁…），算出 6 分制總分，連同原文寫進 vendor_answer_report.md。呼叫失敗時改用內建範例回答繼續。
```

**觀察重點**：

- 五種類型是否各有一位命中，且每個婉拒都附替代方案（沒有「也許」）？
- 模型回答有沒有先講大廠的長處；三個檢查點是否都能讓客戶在對方文件中自己查？
- 檢查器抓到的辯護詞或缺漏照實記錄（每次模型輸出可能不同）。

### 練習 3（選做）：十二個月檢討表

**目的**：用 16.4 的十二個月檢討範本，替自己的「長時程多代理工廠」或求職作品集做一次資產盤點。
**送給練習視窗的提示詞**：

```text
寫 ch16/interactive/twelve_month_review.py：
1. 列出六項資產（客戶或使用者名單、技能庫、藍圖、相依性登記表與發布日誌、實測案例、轉介名單），每項記錄數量與最後更新日期。
2. 以今天為基準，超過 30 天未更新的項目標為「衰退中」。
3. 依每週 20 小時、46 週計算產能，輸入近六個月承諾工時，判斷是否連續三個月超過 75%，並印出應先嘗試的三個替代做法。
```

**觀察重點**：

- 哪些資產是「會複利」、哪些其實在「衰退」？最久沒更新的是哪一項？
- 有沒有只數成果（客戶數、作品數），卻忽略登記表與日誌早已過期？
