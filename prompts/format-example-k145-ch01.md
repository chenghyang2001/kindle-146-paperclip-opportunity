# ch01｜從單體到群體：一次「架構躍遷」的現場觀察

## 這章在講什麼

- 單體代理有兩道物理邊界：一是推理深度受 Token 預算限制（上下文越長、算力成本非線性上升），二是上下文窗口像人的工作記憶，任務一長就忘記前面定好的規矩，作者稱之為「注意力經濟學」。
- 從單體走向群體不只是「多加幾個機器人」，而是一次架構躍遷：問題從「模型夠不夠聰明」變成「多個代理怎麼分工與溝通」。
- 兩種設計隱喻：蟻群（大量簡單代理靠共用訊號媒介自組織，容錯高、擴展強，但寫不出需要連貫意圖的作品）與交響樂（指揮負責意圖、樂手雙向回饋，能處理連貫任務，但指揮成了瓶頸）。實務多半兩者混用。
- 群體的第一個代價是協調成本：代理數超過臨界點後，溝通路徑呈平方成長，數量反而變成負擔；解法是分層、分組，而不是全互聯。
- 預測要同時寫出反方觀點與可驗證指標：成本交叉點、協作邊界、範式轉移三個判準，留給讀者自己追蹤。

## 作者做過的實驗／例子

- 開場：凌晨三點，一位工程師看著十二個微型代理自動合併 PR、偵測並發衝突、回滾再修補，整段過程沒有人介入。
- 重構十萬行舊系統的案例：整包丟給模型只得到空泛原則；拆成十一個模組，做到第七個就忘了命名規範；改用「上下文蒸餾」才明顯變好。
- 協作失速：三個 AutoGPT 分工做研究，反而花了將近兩倍時間，因為一直在協調「誰負責什麼」，還重工又漏工。
- 書中引述的 100 代理排程模擬：10～20 個代理時效能近似線性上升，超過 50 個開始放緩，100 個的產出反而低於 50 個，稱為「排程瓶頸」。

## 教練解說要點

- 先把「代理數 × 單兵產能」和「溝通路徑數 N(N-1)/2」放在同一張表上，臨界點就自己浮現，不用背結論。
- 分層（小組長只跟組員和其他組長溝通）是把平方成長壓回接近線性的關鍵手段，也是蟻群與交響樂混合的具體樣子。
- 指揮角色本身就是單點：它的上下文一樣會爆，所以「誰當指揮、指揮要看多少東西」是設計題，不是預設值。
- 判準要能量測：本章最後三個判準都可以變成數字，演練就是把它們跑出來。

## 演練

### 練習 1：找出群體的協調臨界點（全互聯 vs 分層）

**目的**：用數字重現「代理越多不一定越好」，並看分層架構如何把臨界點往後推。
**送給練習視窗的提示詞**：

```text
寫 ch01/interactive/scaling_sim.py（只用標準庫，random.seed(145)，不可 input()，30 秒內跑完）：
1. 模擬一批 600 個工作單位，交給 N 個代理處理，N 取 1、5、10、20、30、50、75、100。
2. 每個代理每回合產能 1.0 單位，再乘上 random.uniform(0.9, 1.1) 的雜訊。
3. 協調成本兩種架構：
   A. 全互聯 flat：溝通路徑 = N*(N-1)/2，每條路徑每回合吃掉 0.0025 單位總產能。
   B. 分層 tiered：每 8 個代理一組，組內全互聯，加上組長之間全互聯；路徑數照此計算，成本係數相同。
4. 每回合淨產出 = max(0, 總產能 - 路徑數×係數)；算出做完 600 單位需要幾回合（淨產出為 0 視為做不完，記 inf）。
5. 單體基準：N=1 但上下文上限 120 單位，超過後每多 60 單位，產能下降 15%（模擬記憶衰退），最低 0.2。
6. 印一張表：N｜flat 路徑數｜flat 回合數｜tiered 路徑數｜tiered 回合數；並標出兩種架構各自的最佳 N。
7. 把表存成 ch01/interactive/scaling.csv。
```

**觀察重點**：

- flat 的回合數是否先降後升，最佳 N 落在 20～50 之間，100 個代理比 50 個更慢甚至做不完？
- tiered 的路徑數是否遠小於 flat，最佳 N 明顯往後移？
- 單體基準是否因「記憶衰退」而比 N=5 慢很多？

### 練習 2：讓真實模型當指揮，替任務分工

**目的**：讓真實模型扮演交響樂模型裡的「指揮」，把一個任務拆成子任務並決定要幾個代理，再用練習 1 的成本模型檢查它是否過度派人。
**送給練習視窗的提示詞**：

```text
寫 ch01/interactive/conductor_agent.py（只用標準庫，random.seed(145)）：
1. 用 practice/llm_agent.py 的 ask_json 呼叫 claude -p 一次。提示詞：你是多代理系統的指揮，任務是「把一個十萬行舊系統的 11 個模組重構成新架構，並保持命名規範一致」。
   請輸出 {"agents": 整數, "subtasks":[{"id":"T1","desc":...,"depends_on":[...],"mode":"parallel|sequential"}], "shared_memory":"你打算讓所有代理共用什麼來避免忘記規範"}，子任務 5～15 個。
2. 用程式規則檢查（不再呼叫模型）：
   a. depends_on 是否都指向存在的 id、是否有循環（用 DFS）。
   b. 計算關鍵路徑長度（每個子任務算 1 回合）與最大可並行寬度。
   c. 若 agents > 最大可並行寬度，記為「過度派人」；用練習 1 的 flat 成本（0.0025×路徑數）算出這個人數每回合浪費多少產能。
   d. shared_memory 有沒有提到命名規範或設計決策紀錄（關鍵字比對），對應本章「上下文丟失」問題。
3. 把模型原始輸出、四項檢查結果與一段 3～5 行的結論寫進 ch01/interactive/conductor_report.md。claude -p 只呼叫 1 次。
```

**觀察重點**：

- 模型給的代理數是否超過關鍵路徑允許的並行寬度？超過多少就浪費多少，數字要寫出來。
- 依賴圖是否無循環、關鍵路徑是否合理（不是全部都能並行）？
- 結論有沒有回到「指揮本身也是瓶頸、共用記憶用來對抗上下文丟失」？（每次模型輸出可能不同，照實記錄）
