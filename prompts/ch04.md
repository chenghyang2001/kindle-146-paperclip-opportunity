# ch04｜聘用第一批代理：兩個代理、一人一個任務、一條看得見的終點線

## 這章在講什麼

- 在 Paperclip 裡，一次聘用（hire）＝一個角色＋一個 runtime 連線＋一個人類決定。由 CEO 提議的聘用請求要等 board 核准才會成為能工作的員工（不收 heartbeat、沒有憑證、沒有技能）。
- 核准卡片只摘要名字、角色、runtime；彙報線與月預算要點開「完整請求」才看得到。預算是零就沒有上限。三種回應裡「要求修改」最實用；「新聘用需要 board 核准」這個設定可以被關掉，每次安裝都要確認。
- 第一支團隊兩到三人，目標是可讀性（legibility）不是產能：一個蒐集（researcher）、一個塑形（writer），交接在紀錄裡看得見。
- 任務簡報（task brief）五要素：產出、來源、形式、截止、可觀察終點線，再加一條限制和一位審查者。終點線是最常漏的。
- 目標鏈 goal → project → task：任務透過專案繼承目標；空泛的目標讓所有任務都「合理」，具體的目標讓不相干的任務露餡。紀錄只說發生了什麼，不保證做得對。
- 三大錯誤：太多代理、空泛目標、沒有終點線，三者會複利。前十分鐘展示只要：組織圖、一個完成的任務、往上追到目標、乾淨的紀錄，然後問一個問題。

## 作者做過的實驗／例子

- 開場：一位經營者週日聘了八個代理，週三兩個 writer 寫重複的文章、editor 沒東西可編、記帳閒置、log 幾百筆，她說不出這週產出了什麼；終止六個、只留兩個、各寫一個有終點線的任務，週五就有兩樣東西可以指給人看。
- 監督時間算術（示意）：每個代理每天 5 件要看、每件 3 分鐘、時薪 50 美元；8 個代理每天 100 美元，2 個 25 美元，20 個工作日差約 1,500 美元，還沒算模型費。
- 同一週兩家公司：五個角色、目標「產出好內容」→ 週四 90 筆紀錄、零交付；兩個角色、目標「每週五給 10 位客戶一頁摘要」→ 約 20 筆、兩個完成任務、一份摘要。
- 目標對照：「讓業務成長」vs「每週五前寄摘要給 10 位現有客戶，由客戶經理審查」。

## 教練解說要點

- 「聘用是決定不是動作」：用程式模擬摘要卡 vs 完整請求，同一批請求只看摘要會全部核准，看完整請求會退回好幾件。
- 簡報檢查可以自動化：用關鍵字比對七個欄位，就能看出「只寫主題」的簡報 0 分、照模板 7 分；終點線要能被陌生人驗證。
- 目標鏈的價值在「讓不相干的工作現形」，所以練習要故意放幾個不服務目標的任務進去。
- 真實模型能寫出很完整的簡報，但仍要用規則審查；而且簡報合格只代表代理知道何時停，產出對不對仍要打開看。

## 演練

> 說明：練習視窗工作目錄是 practice/。本書沒有附程式，Paperclip 也不安裝：用 Python 標準庫（不可 pip）寫小模擬，檔案放 practice/ch04/interactive/，用 `PYTHONUTF8=1 python ch04/interactive/xxx.py` 執行。需要真實模型時用 practice/llm_agent.py 的 ask／ask_json（走 claude -p），整章最多呼叫 2 次。互動版請直接跑 `bash interactive/ch04.sh 1`～`8`。

### 練習 1：聘用核准閘門——摘要卡 vs 完整請求

**目的**：體會「點開完整請求」這個習慣能擋下多少問題。

**送給練習視窗的提示詞**：

```text
寫 ch04/interactive/hire_gate.py（只用標準庫，不可 input()，30 秒內跑完）：
1. 建 5 筆聘用請求（dict）：欄位 name、role、runtime、reports_to、monthly_budget、task。
   其中 1 筆沒有 reports_to、1 筆 monthly_budget 是 0、1 筆的 task 和前面某筆完全相同，其餘 2 筆正常。
2. summary_card(r)：只看 name、role、runtime 都有值就 approve。
3. full_review(r, seen)：沒有彙報線 → revise；預算 <= 0 → revise；task 和前面任何一筆重複 → revise；否則 approve。
4. 印表：請求｜只看摘要卡｜看完整請求｜理由；最後印兩種做法各核准幾件。
5. 把結果存成 ch04/interactive/hire_decisions.json。
```

**觀察重點**：

- 只看摘要卡是否 5 件全部核准？看完整請求是否只核准 2 件、退回 3 件？
- 三種回應裡為什麼用「revise」而不是「reject」？

### 練習 2：讓真實模型當 CEO 寫任務簡報，再用規則審查

**目的**：拿到一份真實的 researcher／writer 任務簡報，檢查七個欄位是否齊全、終點線能不能被陌生人驗證。

**送給練習視窗的提示詞**：

```text
寫 ch04/interactive/brief_review.py（標準庫＋practice/llm_agent.py，呼叫模型最多 1 次）：
1. 用 ask_json 請模型扮演 CEO agent：公司目標是「每週五寄一頁產業摘要給 10 位 AMR 客戶，由業務經理審查」，
   只聘 researcher 與 writer，各寫一份任務簡報，JSON 欄位：agent、output、source、form、deadline、finish_line、limit、reviewer、brief_text。
2. 存原始輸出到 ch04/interactive/briefs_raw.json；呼叫失敗時改用內建範例（故意讓 writer 的 finish_line 是空字串）。
3. 對每份簡報檢查：七個欄位是否都非空；finish_line 是否含可觀察詞（列、連結、字、頁、清單、都有…）且不含空泛詞（好、高品質、滿意、適當）。
4. 印出每份的缺欄位、終點線、判定 PASS／REVISE，並寫成 ch04/interactive/brief_review.md。
```

**觀察重點**：

- 模型寫的終點線是否具體到「表格至少 8 列、每列都有可開網址」這種程度？
- 內建範例的 writer 為什麼被判 REVISE？
- 審查報告最後要提醒：簡報合格 ≠ 產出正確，還是要打開成品。
