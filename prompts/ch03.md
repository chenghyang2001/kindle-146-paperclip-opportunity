# ch03｜安裝與第一家公司：安裝讓公司成為可能，不讓它受治理

## 這章在講什麼

- Block 1（Build）的開頭：你賣不了自己沒跑過的東西。在可控的測試機上安裝 Paperclip、建立第一家公司，並把每個卡住的地方記下來，它會變成檢查清單與可信的經驗。最常見錯誤是太早雇太多代理。
- 安裝前的六行環境檢查：機器、runtime（官方 2026-10-20 要求 Node.js 24.11 以上）、網路與私有 registry、模型帳號與供應商端上限、維運負責人（ownership）、曝露範圍。最常空白的是第 5 項。
- 一行指令 `npx paperclipai@latest onboard --yes` 建立完整自給的 instance（內嵌 PostgreSQL、本機 port 3100、local trusted mode），但 `--yes` 是讓專案預設替你回答；它不設模型存取，也不設預算政策。
- 第一家公司的 mission 要寫出截止、受眾、產出、來源、審查者；CEO agent 是協調者，重大提議送 board 核准；第一次 heartbeat 沉默多半是模型憑證問題。
- 排錯用內建 `doctor` 分層診斷（runtime、套件下載、本機伺服器、模型連線），沒有備份與客戶同意絕不重設。預設不強制預算是最清楚的商業論點：沒有天花板，就不開心跳。

## 作者做過的實驗／例子

- 開場：一位顧問照快速入門安裝、寫使命、跑心跳，CEO agent 產出提案後停下等她；回頭找預算設定，所有畫面都沒問過。
- 第三方指南與文件鏡像列出較舊的 Node.js 最低版本——憑鏡像說「Node 20 就可以」會讓安裝在客戶面前失敗。
- 版本節奏：2026-10-20 讀取時最新版 v2026.1012.0（10/12），前兩版在 10/5 與 10/1；10/12 版要求升級或回滾前停掉舊伺服器、清掉遺留鎖定資料夾，並改了預算設定的位置與新公司預設指示。
- 時間估計：熟手在乾淨機器只要幾分鐘再加三到十分鐘準備；客戶機器排半天。
- 使命對比：「用尖端 AI 轉型客戶溝通」對比「每週五 9 點前，根據專案筆記替 10 位客戶各產出狀態報告，交客戶經理審查後寄出」。

## 教練解說要點

- 六行檢查把現場的未知變成電話裡的已知；模擬中客戶 A 從二百六十分鐘降到三十一分鐘。檢查要算進合作報價。
- 「安裝成功」與「可以放著跑」是兩件事：模擬安裝後，使命空白、CEO 沒有 adapter、沒有預算政策，第一次心跳「看起來成功」卻沒有產出。
- 使命檢查器用五個欄位判斷能不能被陌生人驗收，最常漏審查者。
- 分層診斷比反覆重跑更快；破壞性修法要先過備份與同意的閘門。
- 預算上限依賴已記錄花費：回報延遲時實際花費會超過上限一點，所以供應商端也要有上限當後盾，並先設上限、試行量測、再報價。

## 演練

> 說明：練習視窗工作目錄是 practice/。本書不安裝真正的 Paperclip，也沒有附程式：用 Python 標準庫（不可 pip 安裝任何套件）寫小模擬，檔案放 practice/ch03/interactive/，用 `PYTHONUTF8=1 python ch03/interactive/xxx.py` 執行。需要真實模型時用 practice/llm_agent.py 的 ask／ask_json（走 claude -p），整章最多呼叫 2 次。

### 練習 1：六行環境檢查＋時間估計

**目的**：把書中的安裝前檢查變成程式，並量出「先檢查」與「現場才發現」的時間差。
**送給練習視窗的提示詞**：

```text
寫 ch03/interactive/precheck.py（只用標準庫，不可 input()，30 秒內跑完）：
1. 定義三台機器（自己的測試筆電、客戶 A 桌機、客戶 B 伺服器），欄位：會不會睡眠、Node.js 版本字串、proxy、私有 registry、供應商端有無上限、維運負責人、曝露範圍。
2. 依六行檢查找出問題：Node 版本以 tuple 比較是否 ≥ (24, 11)；負責人空白或寫「IT 會處理」都算沒有具名負責人；曝露不是「只有本機」要標出需核准。
3. 每類問題給「現場排除分鐘數」與「電話排除分鐘數」，基本安裝 15 分鐘；印出每台機器沒先檢查與先檢查的總分鐘數。
4. 結果存 ch03/interactive/precheck.json。
```

**觀察重點**：

- 哪幾台要先打電話？是不是第 5 項（所有權）最常出問題？
- 先檢查之後，現場時間縮成多少？這就是「把檢查算進合作報價」的依據。

### 練習 2：模擬安裝的治理缺口與 doctor 分層診斷

**目的**：看懂安裝建立了什麼、沒做什麼，並用分層診斷取代盲目重試。
**送給練習視窗的提示詞**：

```text
寫 ch03/interactive/install_doctor.py（只用標準庫）：
1. onboard(yes=True) 回傳一個 instance dict：instance_root、embedded PostgreSQL、web 位址 127.0.0.1:3100、空的 company（mission 空、ceo_agent.adapter=None）、budget_policy=None。
2. 列出治理缺口（使命空、無模型存取、無預算），並模擬第一次心跳：沒有 adapter 時回傳 status=ok 但 output 空。
3. 寫 doctor(env)：依序檢查 runtime ≥ 24.11、未使用私有 registry、port 未被占用、有模型憑證，回傳第一個失敗層與文件化修法；跑舊版 Node、私有 registry、port 被占用、心跳沉默四個案例。
4. 寫 apply_fix(fix, has_backup, client_ok)：修法含「刪除」時，沒有備份或沒有同意就拒絕。
```

**觀察重點**：

- 第一次心跳 status 是 ok，但 output 是空的——你能說出這是「看起來像成功的失敗」嗎？
- 四個案例是否各自停在正確的層？刪資料庫的修法在客戶機器上有沒有被擋下？

### 練習 3：讓真實模型寫使命，再用心跳閘門把關

**目的**：用一次 claude -p 依範本寫第一家公司的使命與 CEO 計畫，再用程式檢查使命五欄位，並實作「沒有天花板就不開心跳」。
**送給練習視窗的提示詞**：

```text
寫 ch03/interactive/first_company.py（只用標準庫＋practice/llm_agent.py，random.seed(146)）：
1. 用 ask_json 呼叫 claude -p 一次：情境是求職中的 AMR／ROS 2 工程師想讓代理每週整理職缺。要求依範本「在［截止］前，為［受眾］產出［產出物］，資料來源是［來源］，由［審查者］使用前檢查」寫一句使命；CEO 計畫最多 3 步且最後一步送 board 核准；附建議上限（美元）與看得出是測試的公司名稱。原樣存 mission_raw.json，失敗就用內建範例。
2. 用正規表達式檢查使命五欄位、計畫最後一步是否送核准、名稱是否含「測試／TEST」。
3. start_heartbeats(ceiling, lag)：ceiling 為 None 時拒絕啟動；每次心跳花 random.uniform(0.3, 0.9)，看到的已記錄花費 ≥ 上限就暫停；比較沒上限、即時回報、回報延遲 2 次三種情境。
4. 結果寫 first_company_report.md。
```

**觀察重點**：

- 模型寫的使命有沒有漏掉審查者？計畫是不是停在「等核准」而不是直接執行？（每次模型輸出可能不同，照實記錄）
- 延遲回報時，實際花費超過上限多少？這就是為什麼供應商端也要設上限。
