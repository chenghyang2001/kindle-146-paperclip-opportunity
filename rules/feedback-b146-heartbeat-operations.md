來源：《The Paperclip Opportunity》（K146）Ch3／Ch6／Ch8／Ch11／Ch12／Ch15／Ch16

本檔收錄「代理系統上線之後怎麼長期跑下去」的規則：喚醒頻率怎麼選、排程要填哪些欄位、上線前要寫清誰擁有什麼、出錯怎麼診斷與升級、備份與更新的順序、交接給別人時要附什麼，以及人該用什麼固定節奏監督。適用於 VPS systemd／cron、雲端 routines、lh-factory、NotebookLM 與 GPB pipeline。

## 13 條規則

### B146-24：喚醒頻率取「能趕上期限的最慢頻率」，並寫下為什麼不更快

設定排程、輪詢或心跳時，先寫出交付期限與一次執行要多久，選還來得及的最慢頻率，並在設定旁寫一句「為什麼不更快」。
**Why：** 「越快越安全」只會把成本與噪音放大，期限才是頻率的唯一依據。
**How to apply：** 等 NotebookLM 生成用 5～10 分鐘輪詢而不是每 30 秒；每週提醒信用 weekly cron；巡視子代理維持 20 分鐘不因焦慮縮短；lh-factory 心跳先算「每天喚醒次數 × 單次成本」。沒有期限的監看改成事件觸發。
來源：Ch8 規則 3、Ch11 規則 1

### B146-25：有時鐘的工作用帶時區的排程，其餘靠事件觸發

有固定時程的工作用帶時區的 cron，其餘靠事件（指派、檔案出現、訊息）觸發；「每隔幾秒醒來看看」的輪詢只留給沒有事件也沒有時程可依的少數任務。
**Why：** 沒標時區的 cron 會在跨機器時差下錯時；沒事件的輪詢大多是空轉。
**How to apply：** VPS cron 一律註明時區（例：UTC 17:07＝台灣 01:07）；Monitor 用「until 條件成立」等待而不是固定間隔；工廠下游在上游單位完成事件時觸發，不定時掃描。
來源：Ch11 規則 2

### B146-26：每個重複工作寫成一張排程卡，缺欄不上線

新增排程任務前填一張卡：一句話交付物、指派的代理、負責的人、cron 與時區、預算上限、審查步驟，以及「上一輪沒跑完又觸發」與「停機期間錯過」各怎麼處理。
**Why：** 併發重疊與錯過補跑是排程最常出事的兩個地方，事前沒決定，出事時只能臨場猜。
**How to apply：** VPS 新 systemd timer／cron 在 README 或 crontab 註解寫上這些欄位；長工作加 lock 防重疊；重開機後預設不補跑錯過的批次，只有錯過就缺的（如月報）才補一次；一次只上線一個新排程。
來源：Ch11 規則 3

### B146-27：上線前先寫下環境與所有權事實

在任何機器上安裝或首次正式執行常駐代理服務前，先寫：機器、runtime 版本、網路與 registry、模型帳號與上限、曝露範圍，以及「誰付費持有帳號、誰持有網域與憑證、壞了打給誰且多久內回應」；維運負責人沒有具體名字就不開工。
**Why：** 服務跑起來之後才問誰負責，答案通常是沒有人。
**How to apply：** 在 VPS、NUC、HP1／HP2／i5 部署 timer、工廠、Remote Control 時，把這些項目寫進專案 README 或看板；「闔蓋會不會睡、誰重開」要明寫；新增 VPS 服務時主動補「擁有者／帳號／通知對象」一段。
來源：Ch3 規則 1、Ch12 規則 1

### B146-28：出錯先分層診斷，未備份不做任何重設

工具或服務出錯時，先用內建診斷或逐層檢查（runtime、套件下載、本機服務、模型連線）找出失敗層，再套該層的文件化修法；刪資料庫、清狀態的重設必須先備份並取得同意。
**Why：** 跳過診斷直接重設，常常修好表面卻把唯一的狀態資料一起刪掉。
**How to apply：** NotebookLM 登入失效、VPS 服務掛掉、工廠狀態檔損壞時，先跑 doctor／status 類指令並回報哪一層失敗；清 checkpoint、刪 state 檔前先複製備份；每次排錯寫進專案排錯紀錄。延伸既有：`feedback-ch04-debugging.md`（四步除錯框架）。
來源：Ch3 規則 5

### B146-29：備份分層列清楚，以「最近還原測試日期」為唯一證明

說「有備份」前，列出資料庫、檔案、設計匯出等各層備份了什麼、沒備份什麼，並記錄最近一次實際還原的日期；沒還原過就標「未驗證」。
**Why：** 沒還原過的備份只是希望，常到要用時才發現缺一層。
**How to apply：** 回報 VPS、NotebookLM 憑證、`~/.claude` 同步的備份狀態用「層｜位置｜最近還原日」三欄表；工廠 checkpoint 要實測過一次「從 checkpoint 續跑」才能在 HANDOFF 寫成可續跑。
來源：Ch12 規則 2

### B146-30：更新順序固定為「備份、停寫、更新、驗證落地」，回滾靠備份

會動到資料或遷移的更新，順序固定為先備份、停掉所有寫入者、更新、讓一個代理跑一次並確認檔案變更真的存下；不假設 rollback 指令能還原資料。
**Why：** 更新時還有寫入者在跑，資料會半新半舊；rollback 指令通常只還原程式不還原資料。
**How to apply：** 工廠或 VPS pipeline 升級引擎前先停 timer、備份狀態檔；驗收看實際產物檔（路徑、大小、hash），不採信子代理「已完成」的敘述。延伸既有：`feedback-ch06-database.md`（3. 遷移附 DOWN 腳本）。
來源：Ch12 規則 4

### B146-31：升級快速發版的工具前，先讀 breaking changes 並在副本試跑

升級 Claude Code、notebooklm CLI、ROS 2 套件等快速發版工具時，先讀目前版本到目標版本之間每一版的 breaking changes，逐條判斷自己的流程有沒有依賴，能的話先在副本或測試環境跑一輪。
**Why：** 跨多版升級時，中間某一版改掉的旗標或預設值最容易被漏看。
**How to apply：** VPS 每日自動升級 Claude Code 加一步「比對 changelog 與自家 skill／hook 依賴的旗標」；notebooklm CLI 升版先在一台 PC 試 login、list、generate，再推到其他 PC 與 VPS。
來源：Ch12 規則 3

### B146-32：維護帶審核日期的相依登記表，每週固定追蹤版本變更

每個專案把依賴的服務、套件、模型、憑證、主機列成登記表（負責人、會壞什麼、上次檢查、下次審核、備案）；每週同一天花固定 30 分鐘讀 release notes、自己承諾過功能的文件頁、相依清單的 issue，把每個變更分成「無影響／待檢視／要行動」三桶寫進一行 log。
**Why：** 變更公告一出就對表，才不會在服務名稱、網域或 CLI 行為改變後才被動踩坑。
**How to apply：** VPS、kindle pipeline、lh-factory 各放一份 `dependencies.md`；在 console 建 `release-log.md`（日期｜工具｜版本｜桶子｜動作），「要行動」類先在一台 PC 測再同步其他機器並更新記憶，「待檢視」類排進月檢。延伸既有：`feedback-ch14-dependencies.md`。
來源：Ch6 規則 5、Ch16 規則 1

### B146-33：事故只在三種情況升級給人，紀錄必寫「接下來改變什麼」

一般故障（空轉、逾時被殺、缺處置結果）自行處理；只有「修正後同錯連三次」「執行超過心跳逾時」「預算暫停卻分不清是否迴圈」才升級給具名負責人。每次事故紀錄都要有「改變什麼」一欄。
**Why：** 每個小故障都升級會讓人麻痺；只寫「已修好」不改變任何東西，同一事故會再發生。
**How to apply：** 回報失敗時固定附「下次改變什麼（規則、設定或監控）」，並寫進對應 memory 或 learnings。延伸既有：全域 CLAUDE.md 主管代理守則第 5 條（同一錯誤連續 3 次就停止）。
來源：Ch12 規則 5

### B146-34：交付長期運作的系統時，先寫好「錯誤產出協議」

交給別人（或未來的自己）長期跑的代理系統，一併寫一頁：單次錯誤怎麼退回與記錄、同類錯誤一週幾次要通知誰、什麼情況才全部暫停、暫停後當天告訴誰、怎麼恢復。暫停是最後一步。
**Why：** 沒事先約定，一出錯不是被忽略就是整個系統被關掉。
**How to apply：** lh-factory、VPS 上的 NotebookLM 收尾腳本、GPB pipeline 的 README 或 HANDOFF 加「錯誤處理約定」：驗證失敗退回撰寫者並記錄、同錯 3 次停止並通知、全停時寫 STOPPED 檔與原因、恢復指令附在旁邊。
來源：Ch15 規則 1

### B146-35：交接文件的擁有者寫接手者，並附退場計畫

交付給別人（客戶、面試官、另一台 PC 或 session）的系統附一頁交接：放在哪、帳號與金鑰登記表位置、備份與最近還原日、更新政策、事故聯絡人、不包含什麼；所有權欄填實際擁有者（接手者），並附退場計畫：鎖定版本、還原步驟、工具停更時怎麼辦。
**Why：** 擁有者寫成做的人，交出去之後就沒人真正持有帳號與資料。
**How to apply：** `drills/*/HANDOFF-*.md` 加「不包含什麼」「鎖定版本」「最近一次從零接手驗證日期」「外部工具失效的替代方案」；給家人朋友的工具與面試展示專案在 README 寫明帳號歸誰、如何自行重建。
來源：Ch12 規則 6、Ch16 規則 6

### B146-36：監督有固定行程，第一個月是量測期，審查會帶數字做決策

長期運作的自動化排好每日、每週、每月固定檢查（各有目的與清單）；新上線的自動化在固定日期開一次審查：事先整理花費對上限、人工介入時間、失敗率與退回原因、排程完成率、使用者監督時間、實際產出，會中逐項決定，並帶兩三個被擋下的失敗案例。
**Why：** 沒排進行程的監督會被跳過；沒有數字的審查只會得出「感覺還好」。
**How to apply：** supervisor-board 巡視拆成每日看失敗與暫停、每週看 QA 失敗統計、每月看額度與權限；每週提醒信、雲端郵件 routines、lh-factory 長跑結束時產出審查紀要（數字、退回原因、決議、下次審查日）。
來源：Ch11 規則 4、Ch15 規則 3
