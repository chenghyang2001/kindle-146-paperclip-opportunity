# K146 第 12 章規則候選：部署、更新與維護

### 規則 1：上線前先寫下三個所有權事實

**規則**：任何會長期跑的代理服務（VPS 排程、工廠、客戶部署），在第一次正式執行前先寫下「誰付費持有帳號、誰持有網域與憑證、壞了打給誰且多久內回應」。
**為什麼**：12.1 開場工作室把公司放在桌機六週，壞掉時「伺服器歸誰」沒有答案；作者說沒有具名聯絡人的伺服器，會一直當機到有人注意到為止。
**怎麼套用**：使用者 VPS（n8n2vps-hub）上的每個 systemd timer、cron、tmux 常駐服務，在專案 CLAUDE.md 或 README 加一段「擁有者／帳號／通知對象」；Claude 新增 VPS 服務時主動補這段，不等使用者要求。給客戶或面試展示的部署也一樣先寫這三行。

### 規則 2：備份分層列清楚，且以「最近還原測試日期」為唯一證明

**規則**：說「有備份」之前，先列出資料庫、檔案、設計匯出三層各自備份了什麼、沒備份什麼，並記錄最近一次實際還原的日期；沒還原過就標「未驗證」。
**為什麼**：12.2 指出匯出不含核准、成本、活動紀錄，資料庫不含代理檔案；文件警告沒還原過的備份只是名義上的備份，範本最常見錯誤是留白「最近還原測試」。
**怎麼套用**：Claude 回報 VPS、NotebookLM 憑證、`~/.claude` 同步等備份狀態時，用「層｜位置｜最近還原日」三欄表；長時程多代理工廠的 checkpoint 要實測過一次「從 checkpoint 續跑」才能寫進 HANDOFF 當作可續跑。

### 規則 3：更新快速發版的工具前，先讀 breaking changes 並在副本試跑

**規則**：升級依賴快速發版的工具（Claude Code、notebooklm CLI、ROS 2 套件、Paperclip 類開源專案）時，先讀目前版本到目標版本之間每一版的 breaking changes，逐條判斷「我的流程有沒有依賴它」，能的話先在副本或測試環境跑一輪。
**為什麼**：12.3 四週五個版本，其中一版讓提及不再觸發 run，直接讓工作室停擺一天半；修正本來只要十分鐘。
**怎麼套用**：VPS 每日自動升級 Claude Code 的流程，加一步「比對 changelog 與自家 skill／hook 依賴的旗標」；notebooklm CLI 升版（如 0.8.x）先在一台 PC 試跑 login、list、generate，再推到其他 PC 與 VPS。

### 規則 4：更新順序固定為「備份、停止寫入、更新、驗證檔案真的落地」，回滾靠備份而非 rollback 指令

**規則**：任何會動到資料或遷移的更新，順序固定為先備份、停掉所有寫入者、更新、讓一個代理跑一次並確認檔案變更真的存下；不要假設 rollback 指令能還原資料。
**為什麼**：12.3 更新指南明說 rollback 只回退程式碼、不撤銷資料庫遷移；新舊版本同時寫同一實例會互相破壞；光有模型回覆不證明檔案被存下。
**怎麼套用**：使用者的多代理工廠或 VPS pipeline 升級引擎前，先停 timer、備份狀態檔，再升級；驗收時看實際產物檔案（路徑、大小、hash），不採信子代理「已完成」的敘述。

### 規則 5：事故只在三種情況升級給人，事故紀錄必寫「接下來改變什麼」

**規則**：代理事故自行處理一般故障（空轉、逾時被殺、缺處置結果），只有「修正後同錯連三次」「執行超過心跳逾時」「預算暫停卻分不清是否迴圈」才升級給具名負責人；每次事故紀錄都要有「改變什麼」一欄。
**為什麼**：12.4 引用官方指南的三種叫人情境；範本最常見錯誤是只記做了什麼、沒記要改變什麼，事故就會重演。
**怎麼套用**：與使用者「同一錯誤連續 3 次就停止並回報」鐵律一致；Claude 回報失敗時固定附「下次改變什麼（規則、設定或監控）」，並寫進對應 memory 或 learnings，而不是只寫「已修好」。

### 規則 6：交付成果附一頁交接文件，名字填擁有者而不是做的人

**規則**：交付給別人（客戶、面試官、另一台電腦上的自己）的系統，附一頁交接文件：放在哪、帳號與金鑰登記表位置、備份與最近還原日、更新政策、事故聯絡人、不包含什麼；所有權欄填實際擁有者。
**為什麼**：12.4 交接文件只回答「什麼歸誰」；範本最常見錯誤是把實作者名字填在客戶的位置，交接後客戶什麼都沒擁有；作者要讀者交給未參與的人測試能否找得到。
**怎麼套用**：console 的 `drills/*/HANDOFF-*.md` 加上「不包含什麼」與「最近一次從零接手驗證日期」；AMR／ROS 2 作品集的展示專案附一頁「怎麼跑、放哪、壞了看哪」，讓面試官不靠口頭說明也能找到。
