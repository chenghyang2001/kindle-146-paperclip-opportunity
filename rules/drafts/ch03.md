# K146 第 3 章規則候選：安裝與第一家公司

來源：《The Paperclip Opportunity》第 3 章（六行環境檢查、安裝做了什麼、使命範本、第一次心跳、doctor 分層診斷、預算缺口）。

### 規則 1：安裝前先填環境檢查，「誰負責維運」必須有名字

**規則**：在新機器或別人的機器上安裝任何常駐服務前，先列出機器、runtime 版本、網路／registry、模型帳號與上限、維運負責人、曝露範圍六項，第五項沒有具體負責人就不開工。

**為什麼**：第 3.1 節六行檢查——最常見錯誤是填了 1～4、第 5 項空白，把技術案變成沒人同意的營運案；自架服務不指定負責人，答案就是「沒人」。

**怎麼套用**：Claude 在 VPS、NUC、HP1／HP2／i5 上部署 systemd timer、工廠、Remote Control 等常駐工作時，交接單先填這六項並寫進專案 README 或任務看板；「闔蓋會不會睡、誰重開」要明寫（對應使用者「PC 永遠開機」的設定）。

### 規則 2：版本需求以官方來源為準，並寫上查證日期

**規則**：引用任何工具的版本需求、預設值或指令時，以官方 repository／文件為準，並在文件中標註「某年某月某日讀取」，不採用第三方教學或記憶裡的版本。

**為什麼**：第 3.1 節同週第三方指南列出過時的 Node.js 最低版本；作者全書替事實標日期，因為兩週內就發了好幾版、預設值會變（3.2 版本節奏）。

**怎麼套用**：Claude 寫 SKILL.md、安裝提示詞（console/prompts/）、面試作品集的技術敘述時，版本號旁加讀取日期；遇到 NotebookLM CLI、claude CLI 之類快速改版的工具，先查 `--version` 與官方說明再下指令。

### 規則 3：「安裝完成」不等於「可以放著跑」，啟用排程前先設上限

**規則**：任何會按排程自動呼叫付費模型或對外動作的代理，在啟用排程之前必須先設好花費上限（平台端＋供應商端兩層），沒有上限就不開排程。

**為什麼**：第 3.2、3.4 節——安裝讓公司成為可能，不讓它受治理；官方預設流程不要求預算政策，作者的習慣是「沒有天花板，就不開心跳」，且供應商端上限是唯一不依賴自己設定正確的控制。

**怎麼套用**：Claude 建 VPS cron、雲端 scheduled task、長時程工廠時，先確認走 Max 訂閱（claude -p、不設 API 金鑰）或有明確的單位預算與次數上限，才啟用 timer；回報時列出上限值與它停下來的條件。

### 規則 4：使命／任務描述要寫出產出、截止、來源與審查者

**規則**：交辦給代理（含子代理、工廠單位）的頂層目標，必須寫成「在什麼時間前，為誰，產出什麼，用哪些來源，由誰審查」的一句話，不寫願景式口號。

**為什麼**：第 3.3 節使命範本——願景式使命讓代理只能猜，猜測的代理在排程上就是花錢；最常見錯誤是漏掉審查者，等於宣告沒人會看。

**怎麼套用**：這與使用者的「交接單五項」相輔：Claude 派子代理時，一句話目標要能讓陌生人判斷完成沒有，並指名驗證代理或使用者是審查者；工廠專案的 mission 欄位照此範本寫。

### 規則 5：出錯先分層診斷，未備份不做任何重設

**規則**：工具或服務出錯時，先用內建診斷或逐層檢查（runtime、套件下載、本機服務、模型連線）找出失敗層，再套用該層的文件化修法；任何刪資料庫、清狀態的重設動作，必須先備份並取得同意。

**為什麼**：第 3.4 節——上網找第一個修法常是刪掉 instance 資料庫重來，在跑了一週的客戶公司上等於摧毀被付錢保管的紀錄；「心跳沉默」最常見是模型憑證問題，是看起來像成功的失敗。

**怎麼套用**：Claude 處理 NotebookLM 登入失效、VPS 服務掛掉、工廠狀態檔損壞時，先跑 doctor／status 類指令並回報哪一層失敗；要清 checkpoint、刪 state 檔前先複製備份；並把每次排錯寫進專案的排錯紀錄，累積成檢查清單（呼應同一錯誤 3 次就停的停止條件）。
