# K146 第 15 章規則候選：交付與留住客戶

來源：《The Paperclip Opportunity》第 15 章（15.1～15.4）。以下規則用在 Claude 與使用者的協作（多代理工廠、VPS 排程、背景 pipeline），以及使用者把代理系統交付給別人時。

### 規則 1：交付時先寫好「壞產出要導致什麼」，暫停是最後一步

**規則**：任何交給別人（或交給未來的自己）長期跑的代理系統，交付時一併寫下一頁「錯誤產出協議」：單次錯誤怎麼退回與記錄、同類錯誤一週幾次要通知誰、什麼情況才全部暫停、暫停後當天要告訴誰、怎麼恢復。

**為什麼**：15.1 開場的客戶因一份日期錯誤的摘要把全部代理暫停六週且沒說；作者的結論是公司沒失敗，是沒人事先約定壞產出該導致什麼，並把錯誤產出協議、暫停與恢復說明、沉默規則列為啟動時必簽的三份文件。

**怎麼套用**：lh-factory 工廠、VPS 上的 NotebookLM 收尾腳本、GPB pipeline 都在 README 或 HANDOFF 加一段「錯誤處理約定」：單位驗證失敗退回撰寫者並記錄，同一錯誤連續 3 次停止並通知（與使用者既有的停止條件對齊）、全停時寫 STOPPED 檔與原因、恢復指令附在旁邊。

### 規則 2：「沒有消息」不算好消息，長時間工作要有固定回報節奏

**規則**：派出長時間背景工作後，約定固定回報節奏（例如開始後第一次、之後定時），並把「該回報卻沒回報」本身當成要處理的訊號，不把安靜解讀成一切正常。

**為什麼**：15.1 的沉默規則要求每週短訊與「就算只回沒問題也要回」，讓沉默從模糊變成訊號；15.2 列出失去參與的訊號：沉默、佇列多日沒人碰、統計停止成長、例行程序無故略過、全部暫停。

**怎麼套用**：Claude 派背景子代理或 VPS 工作時，同時開 Monitor 盯 log 停滯（使用者既有的「長工作要自己盯進度」原則），把「log 超過 N 分鐘沒新行」「DONE 檔遲遲沒出現」「計數不再增加」列為警示條件；偵測到就當下查原因並回報，不等使用者問。

### 規則 3：第一個月是量測期，審查會要帶數字和失敗案例做決策

**規則**：新上線的自動化（排程、工廠、郵件 routine）上線後安排一次固定日期的審查：事先整理花費對上限、核准或人工介入時間、失敗率與退回原因、排程完成率、使用者自己花的監督時間、實際產出，會中逐項做出決定，並帶兩三個被擋下的失敗案例。

**為什麼**：15.2 的六項量測與 45 分鐘董事審查議程，強調「是決策會議不是報告」，每一項以決定或具名負責人收尾，並要求誠實展示被評分表攔下的失敗。

**怎麼套用**：每週一的 Anthropic harness 提醒信、四個雲端郵件 routines、lh-factory 每次長跑結束時，Claude 產出一段審查紀要：六項數字、被退回的單位與原因、決議（上限調整、規則修改、停用哪個 routine）、下次審查日期，寫進 supervisor-board 或對應 repo。

### 規則 4：算淨價值時一定扣掉使用者自己的監督時間

**規則**：評估某個自動化值不值得繼續跑或擴大時，淨價值＝產出省下的時間價值－模型與主機與維運成本－使用者自己花在審查、修正、盯進度的時間；不可省略最後一項。

**為什麼**：15.2 指出客戶最常低估的就是自己的監督時數，並在三十天審查紀要範本中把「漏掉客戶自己的時數，讓淨值看起來比實際好」列為最常見錯誤；本章演練中漏掉 7 小時會讓淨值被高估約三成。

**怎麼套用**：使用者問「這個 pipeline／工廠／VPS 服務值不值得留」時（例如 VPS 遷移 Managed Agents 評估、API 使用盤點），Claude 的試算表固定列一行「你自己花的時間（小時 × 時薪）」，並請使用者估實際花在檢查與修錯的時數，而不是只算 API 費用。

### 規則 5：數字撐不起持續費用時，誠實建議較小的方案

**規則**：當持續性服務的費用（訂閱、月約、常駐 VPS 服務、常駐代理）超過它實測淨價值的一半，就建議降級為較小、定期的檢查（例如每季或每年一次審計），並把這個建議寫成書面選項。

**為什麼**：15.3 以「月費不超過實測淨月價值一半」檢驗維護合約；淨值 1,360 美元的客戶一半只有 680 美元、低於 2,500 美元錨定底線，就不該提月約，改建議年度 Governance and Budget Audit，並強調「說不本身就是一種服務」。

**怎麼套用**：Claude 在使用者的訂閱盤點（Audible、YouTube Premium、CapCut 等）、VPS 常駐服務或 Max 以外的 API 支出檢視時，套用「費用 ≤ 實測淨值一半」檢查；不通過就提出降級選項（改年度、改按次、停掉改手動），並附上計算。

### 規則 6：案例與作品集只寫經同意、有日期、可重現的數字，並寫出沒成功的事

**規則**：撰寫作品集、案例研究、對外貼文時，每個數字都附日期與假設，必須包含一件沒成功的事與結果的限制；涉及他人（前雇主、客戶、場域）的內容先取得同意，未經同意不放名稱與資料。

**為什麼**：15.4 的案例研究五段結構（情況、建了什麼、量了什麼、沒成功的事、限制）與保密原則：未經明確同意不放客戶資料，即使遮蔽；最常見錯誤是只寫數字不寫產生它的假設。

**怎麼套用**：AMR／ROS 2 作品集與面試簡報中，每個專案頁加「沒成功的事」與「限制」兩欄；AIHCR 等公司專案只用示範版資料（呼應既有「aihcr-daily 公開頁勿展示」記憶），數字附日期與來源路徑。
