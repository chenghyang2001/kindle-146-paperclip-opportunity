# K146 第 16 章 規則候選（含結論與附錄）

> 來源：《The Paperclip Opportunity》第 16 章〈Staying Current, Saying No, and Compounding the Practice〉、結論〈The Board Seat〉、附錄 A～F。狀態：草稿，待使用者核准。

### 規則 1：每週固定 30 分鐘做「三來源、三桶子」版本追蹤

**規則**：對自己依賴的快速變動工具（Claude Code、NotebookLM CLI、lhf 引擎相依套件），每週同一天花固定 30 分鐘，依序讀 release notes、自己承諾過功能的文件頁、相依清單的 issue，並把每個變更分成 No effect／Review／Act 三桶寫進一行 log。

**為什麼**：16.1 指出「什麼都讀」會變第二份工作、「什麼都不讀」會從客戶口中才知道預設改了；產出不是知識而是分類，Act 一週內在 staging 測過再通知受影響的人。

**怎麼套用**：在 `console/` 建一份 `release-log.md`，每行「日期｜工具｜版本｜桶子｜動作」。像 NotebookLM 改名、CLI 報 CSRF 這類過去踩過的坑，屬於 Act：先在一台 PC 測、再同步到 HP1／HP2／VPS，並更新 MEMORY 對應條目。Review 類排進月檢，不當場改設定。

### 規則 2：設定類知識一律附日期，過期就當不可信

**規則**：寫進記憶、CLAUDE.md、交接文件的預設值、畫面操作、adapter 狀態、價格、版本數字，一律附「查證日期＋出處」；沒有日期的數字不得當作事實引用。

**為什麼**：16.4「複利 vs 衰退」表把「預設值與畫面知識」「adapter 狀態筆記」「沒附日期的數字」列為隨版本衰退的資產；16.1 也要求每個數字帶日期與官方來源。

**怎麼套用**：記憶條目若寫「上限 Plus 200／Pro 500」「到期 12/15」這類值，加上 `（2026-11-xx 實測）`。session-end 的 Infra 漂移檢查順便掃無日期數字。面試作品集裡的工具版本、benchmark 數字也照此處理，被問到才不會講錯。

### 規則 3：說不要早、要一句理由、要附替代方案

**規則**：遇到超出能力或不該接的請求（求職面試中被問到不熟領域、他人委託、代理工廠被派到不適合的單位），在第一時間用一句話說明落差，並立刻給一個較小的可行方案或轉介對象，不要軟化成「也許」。

**為什麼**：16.2 五種不適配客戶的共同模式：拒絕是說明落差而非評價人，每次都配一個替代方案；最常見錯誤是把拒絕軟化成 maybe，讓對方乾等。

**怎麼套用**：AMR／ROS 2 面試被問到沒做過的（例如 RAG、GCP 量產）時，用「我目前沒有實際做過 X；我做過的是 Y，可以在 Z 週內補上」句型。lhf 工廠的客觀驗證若判定某單位不適合自動化，回報要寫「不適合原因一句＋改由人做哪一段」。

### 規則 4：每個自動化系統都要有具名的「董事席」與回應時窗

**規則**：任何會自己跑的代理流程（VPS cron、NotebookLM 批次、長時程工廠、雲端 routines），先寫下誰核准、誰可暫停、多久內要回應、錯過時窗誰接手；沒人坐得進去的座位就不要上線。

**為什麼**：結論〈The Board Seat〉區分「設計座位」與「交出鑰匙」；附錄 B 指出章程最常見的失敗是「誰決定」欄位空白，讓決策變成沒有擁有者的設定。

**怎麼套用**：在 `supervisor-board.md` 每個長工作列加「核准者／暫停方式／回應時窗」三欄。lh-factory 的「工作核准」步驟要寫明等待超過幾小時就自動暫停而不是繼續跑；VPS 寄信類腳本把「暫停開關」寫在 run.log 第一行。

### 規則 5：預算上限先於第一次心跳，且當作強控制而非精確控制

**規則**：任何會花錢的代理（API 呼叫、雲端 routine）在第一次執行前先設定每代理上限與 80% 警示，並預留「進行中工作可能超過上限」的餘裕。

**為什麼**：附錄 B／C：預設安裝不會替你設預算，所以預算政策要在第一小時、第一次 heartbeat 之前寫好；進行中的 run 會在停止生效前超支，上限要低於你無法承受的損失。

**怎麼套用**：對照 API 使用盤點的三處（line-gmail-bot、拍五 intent_proto、GitHub PR 代理），在 console.anthropic.com 為各自設定上限並記錄日期；新增會打 API 的腳本時，在 README 寫「月上限／警示比例／誰被通知」三欄，不寫就不部署。

### 規則 6：交接文件的擁有者必須是接手的人，並附退場計畫

**規則**：交付給別人（或另一台 PC、另一個 session）的系統，交接單上的帳號、資料、備份擁有者寫接手者，並附一頁退場計畫：鎖定的版本、還原步驟、工具停更時怎麼辦。

**為什麼**：16.3 五項延續性措施（鎖版本、備份還原、帳號資料歸客戶、每季檢查、退場計畫）；附錄 C 指出交接單若把顧問寫成擁有者，案子結束後客戶什麼都沒有。

**怎麼套用**：`HANDOFF-*.md` 加「鎖定版本」「最後還原測試日期」「依賴的外部工具若失效的替代方案」三段；對外作品（給太太或朋友的工具、面試展示專案）在 README 寫明帳號歸誰、如何自行重建。
