# 第 6 章　技能、連接器與記憶（Skills, Connectors, and Memory）

> 所屬區塊：BLOCK 2・ORGANIZE（組織）
> 本章副題：一家公司需要哪些 skill 和連線？給多少權限就夠？

## 本章核心問題

代理依賴的某一條連線被官方退役（retired）了，會發生什麼事？

作者用一個綜合案例開場。2026 年夏末，一位顧問替客戶做了一家「週報公司」：代理每週要從六個外部應用程式抓資料，包括客戶資料庫、文件庫、行事曆和帳務工具。顧問沒有逐一串接，而是透過一個 broker 整合服務，一條連線就通到全部工具。頭兩個月運作順利，週報準時送出。

接著 Paperclip 發了一次更新，把舊版 broker 退役。根據 2026 年 10 月 1 日的 release notes，經由舊 broker 建立的連線全部停擺，沒有自動遷移，操作者得手動刪掉每一筆退役的連線紀錄、再重新設定替代路線。在那之前，代理拿不到背後的工具。客戶下一份週報的「客戶」和「帳務」兩段整個空白，而顧問是從客戶那邊才知道出事——客戶則是看到報告才發現。

作者強調：這家公司的設計沒有錯，角色清楚、goal chain（目標鏈）乾淨、結構也符合 Blueprint（藍圖）。壞掉的是一個「沒人寫下來、也沒有排定檢查日期」的相依項目。修好只花了一個下午，但教訓更長：代理依賴的每一條連線，都是別人給的承諾，而承諾會到期。

## 6.1 Skill 與 Skill Studio

### skill 是什麼

skill 是「把你的判斷安裝進代理」的方式。會寫好 skill 的顧問，賣的是一般公司給不了的東西。

在 Paperclip 裡，skill 是代理處理某類任務時載入的可重用指令包。2026 年 10 月 20 日閱讀的官方文件描述得很具體：一個資料夾，裡面有一份主指令檔（短短的檔頭加上程序本文），再加上選用的參考資料。檔頭可以放名稱、描述和短識別碼；名稱和描述是建議必填，識別碼是選填。

**描述（description）比本文重要。** 文件直接說它是一段 routing description（路由描述）：說明這個 skill 何時該用、何時不該用。要調整的是描述，不是本文。運作方式是：每次 heartbeat 開始時，代理會看到它能用的每個 skill 的名稱和描述，只有描述對上眼前工作時，才載入完整本文。這讓每次執行比「把所有程序貼進每個提示詞」便宜得多；反過來說，描述含糊的 skill 會在錯的時間被載入，或永遠不會被載入。

### skill library 與附加

skill 存放在公司的 skill library（技能庫），有已安裝、探索新 skill、依來源分類、自己撰寫等檢視。**安裝只是加進庫裡，不會附加給任何代理。** 要從 skill 頁面或代理的 skills 分頁把它附加到某個代理，變更在該代理下一次執行時生效。文件建議只附加給需要的代理；而且 skill 以公司為範圍，替 A 客戶公司寫的 skill，要在 B 客戶公司另外安裝。

### Skill Studio 與版本

撰寫工具叫 Skill Studio。文件描述的建立流程有四步：基本資料、設計、內容、審查；工作區有檔案編輯器、測試輸入和一次測試執行。先存檔再測；測試執行會建立一個隱藏任務，讓你看代理到底有沒有照指令做。每次存檔都產生新版本，附可還原的歷史。

版本在商業上很重要：客戶說「上週四起週報語氣變了」，版本歷史會告訴你 skill 有沒有改、代理當時用的是哪一版。釘選版本（pinned version）則讓一個任務做到一半的代理，繼續用它開始時那一版。

### 兩個要小心的預設

1. **代理預設可以建立、匯入、編輯、測試、移除 skill。** 公司層級的 skill policy 可以依代理、依 skill、依來源限制這些動作。能改自己指令的代理，會漂離你測過的程序。請把 skill policy 當成控制層的一部分；第 9 章會談哪些決定屬於人，「誰能改 skill」就該列在上面。
2. **skill 的來源。** 庫可以從 GitHub repo、連結或路徑匯入；文件提醒，來自 gist 或連結的 skill，在附加給高信任代理之前，要像第三方程式碼一樣審查。skill 是代理會服從的文字；陌生人寫的 skill，就是陌生人給的指令。2026 年稍早公開討論提到過一個共享的 skill 與公司範本市集，但 10 月 20 日的文件並未描述這樣的市集，導覽列上的 Team Catalog 頁面作者也未評估，本書內容不依賴兩者。

### 好 skill 的三個條件

夠窄、可測試、寫明情況不符時怎麼做。「寫好一點」是願望；「摘要來源時，用一句話寫出論點、附發布日期，若沒有日期就寫 date not found，不要估計」才是程序。**失敗行為一定要明寫**：沒有規則處理缺口的代理會自己即興，而即興正是捏造統計數字的來源。

作者建議五個適合多數小企業的 skill（取自附錄 A 的四個職能，是建議而非產品功能）：

| skill | 管什麼 |
| --- | --- |
| source-and-cite | 論點怎麼連結來源，沒有來源的怎麼標記 |
| house-style | 客戶的寫作方式，附三個好範例、一個壞範例 |
| handoff-note | 代理完成時貼出的簡短狀態訊息，讓審查者 30 秒讀完 |
| escalation | 何時停下來問人：缺來源、超出範圍、數字看起來不對 |
| acceptance-check | 把任務的完成標準變成送審前要跑的小清單 |

### skill 值不值得：作者的試算（明列假設）

- 公司每月產出 40 份成品，審查者目前每份花 15 分鐘補缺漏的引用。
- 加上 source-and-cite skill 後，假設修正時間降到 5 分鐘：每份省 10 分鐘 × 40 份 ≈ 每月 6.7 小時，以時薪 50 美元計約 333 美元。
- 扣掉成本：撰寫加測試 3 小時（150 美元，一次性）、每月維護 1 小時（50 美元）。
- 第一個月淨約 133 美元，之後每月約 283 美元。審查本身仍存在，只是變短。

### 範本：skill 描述（路由行）

「Use when ｛觸發情境｝。Do not use when ｛不該觸發的情境｝。Produces ｛產出｝。If ｛缺少的輸入｝, ｛明確的備案行為｝。」

最常見的錯誤：描述寫成 skill 的「主題」，而不是「該載入它的情境」，結果代理在錯的時間載入。

**多數人的做法**：寫一個叫「Great Content」的 skill，內容是「用品牌語氣寫出清楚、吸引人的文章」，附加給每個代理，從不測試。
**有效的做法**：寫「Source and cite」，描述是「編輯或摘要含事實論點的素材時使用；寫標題時不要用」；寫明三個步驟、缺來源時的行為、變更註記範例；只附加給 editor；用三個輸入測試（其中一個是沒有來源的論點），記下它在哪裡失敗。

## 6.2 連接器：選得少、給得少

選出這個職能少了就跑不動的兩三個 connector，每個只給「剛好夠用」的最小權限，因為每多一條連線，代理能做的事和能出錯的事都跟著變多。

connector 把公司接到外部服務：收件匣、行事曆、文件庫、聊天工具、程式碼 repo。它讓代理在客戶原本就用的工具裡做事，也是客戶覺得最刺激的部分——正因如此要謹慎。10 月 20 日的文件列出一份 connector 目錄，導覽列上目錄徽章顯示 62、整個連接器區段徽章顯示 78；兩個數字都只是當天的快照、量的也不是同一件事。**目錄裡有多少個不重要，你授出去多少才決定風險。**

**從職能出發，不從目錄出發。** 回到第 5 章 Blueprint 中標記為代理執行的步驟，逐一問：代理必須「讀」哪個外部系統、必須「寫」哪個？週報只需要讀某一個資料夾的專案筆記，所以要的是一條唯讀連線，而不是整個文件庫。分類代理要讀共用收件匣並貼標籤，但不寄信。把答案寫成一張短表：步驟、服務、需要的動作、最小權限。多數小職能只要兩三列；看起來需要十列的，通常其實是兩個職能。

**存取模型幫你保持精簡。** 依文件描述，連線和「誰可以用」是分開的：授權可以給整個組織、某個使用者或某個代理，一條連線可以有共用預設加上個別授權。gateway 在呼叫時套用最終生效的政策。每個目錄項目宣告它支援的動作和風險等級，動作可設為 Allowed、Ask first 或 Off；Ask first 的動作會等人回應審查請求。白話說：你通常可以設定「某代理可以讀某服務」、「某動作要先給人看」。原則是：授權給代理而不是組織、讀優先於寫、只給完成這一步最窄的動作。

**身分和權限一樣重要。** 連線以某個身分登入，那個身分看得到什麼，代理就看得到什麼。10 月 5 日的 release notes（10 月 20 日閱讀）描述了一個會顯示「連線以誰的身分登入、哪些代理能用」的設定畫面；9 月 16 日的 release notes 提到 GitHub 存取改用持久的個人身分取代共用 token。這是產品對同一個問題的回答：代理以擁有者身分登入，就能做擁有者能做的一切。只要服務允許，就替代理開專用帳號，只給這一步需要的窄權限，擁有者自己的憑證不進公司。專用帳號也讓紀錄讀得懂，因為代理的動作不再和本人的動作混在一起。

**還有一個預設和連接器直接相關。** 10 月 1 日的 release notes 列出一項破壞性變更：coding agent（Claude Code、Codex、Gemini CLI、OpenCode、Kimi、Grok）預設改為 full auto（全自動），各 adapter 頁面有說明怎麼調回來。實際意義是：拿到廣泛 connector 權限又停在預設的代理，可能在 runtime 層不經詢問就動手。第 10 章會談顧問的資安姿態；現在先把每個 connector 都當成「刻意設定為限制性」的決定，而不是「沒出事前都很方便」的捷徑。

### 範本：連接器存取表

「步驟：｛step｝。服務：｛service｝。需要的動作：｛讀或寫，什麼｝。授權給：｛一個代理｝。登入身分：｛專用帳號｝。最小權限：｛最窄可用｝。需要先給人審：｛是否，哪個動作｝。審核日：｛date｝。」

最常見的錯誤：因為只要點一下，就在組織層級授權——這等於讓現在和未來的每個代理都拿到同樣的範圍。

**多數人的做法**：把擁有者的信箱、整個文件庫、行事曆、帳務工具和聊天工作區都接上，理由是目錄裡有、「代理也許用得到」，而且以擁有者身分登入。
**有效的做法**：替 Researcher 接上共用專案資料夾、唯讀；Writer 什麼都不接；Editor 只對一個輸出資料夾有寫入權。用代理專用帳號，每月審一次授權清單，移除沒用到的。

## 6.3 系統記得什麼

除非你給代理「找得到的東西」，否則它在 heartbeat 之間什麼都不記得；所以要設計代理「查得到」的上下文，不要依賴它「得用猜的」上下文。

文件寫得很清楚：代理不是持續運行的。它們以短暫的 heartbeat 醒來，之間處於休眠，不花預算、執行程序裡也不保留記憶。這和第 1 章的圖像一致，但有個常被忽略的後果：上一次 heartbeat 結束時代理知道的一切，若沒存到下一次讀得到的地方，就消失了。以為代理「知道」客戶上週的偏好，是在假設架構沒有提供的東西。

**哪些東西會保留**（10 月 20 日文件）：

- adapter 在每次執行後儲存 session state（階段狀態），下次醒來時還原，所以 runtime 能接續對話；重設則會清掉。
- 代理自己的 agent folder（代理資料夾）在執行結束時同步回去，代理寫進資料夾的筆記下次可用。
- 交付物放在 task workspace（任務工作區），和代理資料夾分開。
- run record（執行紀錄）保存歷史、逐字稿、log 和成本，供稽核用。
- 每次執行，代理還會收到自己的身分、觸發原因、指令、Paperclip 內建的操作指引，以及附加的 skill。其他需要的一切，都得從資料夾、session 或 Paperclip 本身讀取。

**比描述更重要的注意事項：**

- 代理檔案**沒有版本歷史**，只保留目前檔案；兩次執行、或一次執行與一次手動編輯改到同一個檔案時，**最後完成的同步獲勝**，被蓋掉的版本救不回來。
- session 可能在執行中途輪替，所以不保證每次 heartbeat 都能延續。
- 資料夾有容量上限，超過時**不會停止代理**：該次執行對資料夾的變更被丟棄、出現警告，下次從上一個已存狀態開始。成功的任務不代表檔案變更有存到，要檢查該次執行的 sync receipt（同步回條）。
- 代理檔案存在實例的儲存空間、不在資料庫裡；只備份資料庫的備份會漏掉它們。第 12 章談備份，這就是那個問題重要的原因。

**設計上的推論：** 把代理需要知道的寫下來，放在它找得到的地方。客戶偏好的語氣放在 skill，或放在指令指向的參考檔；五個來源的清單放在任務上；長期專案的現況放在一個短筆記檔，代理每次結束時更新、下次開始時讀取。不要把週流程的延續寄託在「代理會記得」：依賴上週數字的週報，應該從檔案或上一個任務讀上週數字，而指令要這樣寫明。

**找得到 vs. 用猜的。** 指令寫「照客戶平常的格式」，代理就會猜平常的格式是什麼；寫「照 references 裡那個檔案的格式」，代理就會去讀。每一句「as usual」「as before」「你知道我們的風格」都是會發生猜測的地方，把它們各換成一個代理打得開的指標。

**多數人的做法**：告訴 Writer「沿用上週摘要的結構，維持我們討論過的語氣」，以為代理記得兩者。
**有效的做法**：結構放參考檔，三個好範例放語氣檔；每次執行結束，在筆記檔追加一行記錄用了哪些來源；每週檢查一次筆記檔。

**記憶連接器（memory connectors）**：產品也列出把代理接到外部記憶服務的連接器，10 月 20 日文件把它們標為 experimental 且預設關閉，列出的支援服務有 Mem0、Zep、Supermemory、Cognee、Honcho。不要拿 experimental 功能做客戶案；客戶問到時，說明它是什麼、目前狀態，並提議先在你自己的測試公司試。

記憶是設計任務，不是產品功能：決定每個代理必須知道什麼、寫在找得到的地方、確認有存到，永遠不讓流程依賴代理的記憶。

## 6.4 相依項目與審核日期

每個 skill 來源、connector、runtime 和模型供應商都是相依項目，每一項都需要一位負責人、上次檢查日期和下次檢查日期。

回到退役的 broker，這是個乾淨的案例。10 月 1 日 release notes 的事實是：退役第三方的舊版 broker 整合；既有連線停擺；沒有自動遷移；操作者要刪除每一筆退役連線並設定替代路線——notes 描述為一條較新的 aggregator 路線，原本藏在 experimental 設定後面，從 10 月 5 日的版本起不再受限。在那之前，代理拿不到退役的工具。connector 文件把 Composio 的設定標為未驗證，所以在承諾之前先測任何替代方案。這次 release 也改了其他預設、移除了其他東西——這很正常：快速演進的專案會移除與替換，而 release note 是唯一的預警。

什麼能抓到它？不是更好的設計，而是一張登記表。若顧問保有一頁「公司依賴什麼、每一項上次何時檢查」的清單，10 月 1 日的 release 就會被拿來對照那張清單；broker 那一列會寫明它消失時什麼會壞、誰負責、備案是什麼。故障就會是一個排好的下午，而不是給客戶的驚喜。

### 範本：dependency register（相依性登記表）

| 相依項目 | 類型 | 負責人 | 變動時會壞什麼 | 上次檢查 | 下次審核 | 備案 |
| --- | --- | --- | --- | --- | --- | --- |
| ｛broker 或 connector｝ | Connector | ｛名字｝ | ｛哪一步停｝ | ｛日期｝ | ｛日期｝ | ｛替代方案｝ |
| ｛skill 來源｝ | Skill source | ｛名字｝ | ｛哪個行為改變｝ | ｛日期｝ | ｛日期｝ | ｛釘選副本｝ |
| ｛runtime｝ | Runtime | ｛名字｝ | ｛哪個角色沒人做｝ | ｛日期｝ | ｛日期｝ | ｛替代方案｝ |
| ｛模型供應商｝ | Model | ｛名字｝ | ｛品質或成本變動｝ | ｛日期｝ | ｛日期｝ | ｛替代方案｝ |

每一欄都有具體用途：負責人欄逼出一個名字，和第 3 章的 uptime owner 是同一種紀律；「會壞什麼」欄逼你把相依項目追溯到 Blueprint 的某一步，告訴你故障有多嚴重；備案欄逼你現在就問那個不舒服的問題；日期讓登記表是活文件，而不是一張照片。

**搭配季度審查。** 每季一次（實務上也包括任何你知道會碰到清單項目的 release 發布時），花大約 30 分鐘：讀上次審查以來的 release notes，找出提到的每個相依項目，更新日期，寫下需要行動的事。第 16 章會把這變成追蹤整個專案的每週習慣；這裡的重點更窄：審核日期是「承諾去看」，而你承諾去看的，就是你會注意到的。

**多數人的做法**：整家公司建在單一整合上，記在腦袋裡，再從客戶口中得知它退役了。
**有效的做法**：交付當天就把每個相依項目列進登記表，寫上上次檢查日期並排定下次審查；有 release 發布時，先在 notes 裡搜尋登記表上的每個名字，再動客戶的公司。

## 實作清單（本章 Action）

1. 在測試公司替一個任務寫一個 skill，套用 6.1 的路由描述範本：何時用、何時不用、產出什麼、缺輸入時怎麼做。
2. 存檔後只附加給一個代理，用三個輸入測試：一般、缺一項、超出範圍。逐一記錄代理是否載入、是否遵循、在哪裡失敗。修好一個失敗，存成新版本。
3. 用 6.2 的存取表列出測試公司用到的每個 connector：服務哪一步、最小權限、登入帳號、是否有動作要等人。移除任何對不上 Blueprint 步驟的 connector。
4. 以這份清單開一張相依性登記表，加上 runtime 和模型供應商，寫上每項的檢查日期與下次審核日期。保留這張表，第 7 章會加入 runtime。

## 本章小結

- skill 是一小段有版本、可測試的判斷；它逼你說清楚「好的工作長什麼樣」。客戶看到依自己標準建起來的 skill 庫，看到的是一般公司給不了的東西。
- skill 告訴代理怎麼做事；connector 決定它碰得到什麼，風險在後者。選得少、給得少、用專用帳號。
- 記憶是設計任務：寫在找得到的地方、確認有存到、不讓流程依賴代理記得。
- 最貴的失敗不是設計錯誤，而是沒人盯的相依項目；解藥很便宜：一張表、一個名字、一個日期。同一個 broker 退役，對一位顧問是驚喜，對另一位只是登記表上的一行。
- 公司是一組選擇，而連線是別人可以撤銷的選擇。本章的功夫不是接更多，而是知道自己站在什麼上面、上次是什麼時候看的。
