# 第 3 章｜安裝與第一家公司（Installation and Your First Company）

> 所屬區塊：Block 1・Build（建置），第一個 BOARD 階段的開頭。

## 區塊導言：沒跑過的東西賣不出去

第 3、4 章要在你能控制的機器上安裝 Paperclip、建立有 mission（使命）和 CEO agent 的公司、看第一次 heartbeat（心跳）、雇小團隊、讀紀錄。這家測試公司是之後練預算、練核准、做 demo、提前撞到失敗的地方。

- **安裝不一定順利，這在商業上是資產。** 客戶的機器總有舊 runtime、公司網路、私有套件庫、會睡著的筆電、不確定誰在管。親手解決過困難安裝的顧問比只看過乾淨安裝的人可信。每個卡住的點都寫下來，變成檢查清單與故事。
- **最常見錯誤是太早雇太多代理。** 第一天八個代理像進展，第三天兩個重疊、一個閒置、活動紀錄讀不下去。修法永遠是砍到剩兩個重來。
- Paperclip 發版頻繁，所以本書說明安裝「做了什麼、為什麼重要」，替事實標日期，確切指令與標籤以官方文件為準。

## 本章核心問題

為什麼整個設定過程，沒有一步問過這家公司可以花多少錢？

## 開場情境

一位顧問打下快速安裝指令、什麼都沒回答，幾分鐘後儀表板打開：公司有名字、空的使命欄、組織圖頂端一個 CEO agent。她寫了使命、讓 CEO 跑第一次心跳，代理產出提案後停下來等她。接著她問了會問任何客戶的問題：這家公司能花多少？回頭翻每個畫面——沒有欄位、沒有提示、沒有政策。她不粗心，完全照快速入門做；她找到的是「預設設定」與「安全設定」分道揚鑣的第一個地方。

## 3.1 安裝之前：環境與需求

大部分安裝失敗由環境決定，而客戶的環境不由你挑。

- **Runtime**：Paperclip 是 Node.js 應用。官方 repository（2026-10-20 讀取）要求 Node.js 24.11 以上；從原始碼建置另需 pnpm 9.15 以上；用本機 coding agent 訂閱登入需 Python 3 與供應商 CLI。同週流傳的第三方指南列的是較舊版本——不是說謊，是抄了過時需求。**來源不一致時，以官方為準，並在約客戶當天查證。**
- **機器**：self-hosted（自架），預設跑在本機、只在本機 port 3100 提供介面，部署指南稱為 local trusted mode（不登入、只綁 loopback、一位受信任操作者）。適合測試公司，不適合客戶：闔上的筆電，代理不會醒。
- **所有權（ownership）**：自架代表有人要負責 uptime、更新、發現伺服器停了。不問，答案就是「沒人」。安裝前寫進合作範疇，不接受沒有名字的「IT 會處理」。
- **網路**：代理要能出站連到模型供應商。問客戶技術窗口：不經 proxy 能上網嗎？有私有套件 registry 嗎？任一個「是」，就是你第一個小時排錯的原因。
- **憑證**：每個做事的代理都需要模型存取（API key 或訂閱），帳號擁有者就是帳單擁有者。測試機請用在供應商端設了花費上限的 key——它是唯一不依賴你設定正確的控制。

### 六行環境檢查（Pre-install environment check）

| # | 項目 | 要填 |
| --- | --- | --- |
| 1 | 機器 | 廠牌與系統；何時開機？會排程睡眠或重開嗎？ |
| 2 | Runtime | 已裝 Node.js 版本；官方某日期要求的版本 |
| 3 | 網路 | 能直連供應商嗎？有 proxy 或私有 registry 嗎？ |
| 4 | 模型存取 | 誰付費、誰擁有、供應商端有沒有上限？ |
| 5 | 所有權 | 交付後誰負責 uptime、更新、重開？寫名字 |
| 6 | 曝露範圍 | 只在本機可連，還是其他裝置也可？誰核准？ |

最常見錯誤：填了 1～4、第 5 項空白，把技術案變成客戶沒同意要營運的營運案。對比：多數人約好週四到場才發現 runtime 舊兩個大版本、網路擋下載、沒人知道誰管伺服器；有效做法是預約前寄出六行檢查、用十五分鐘電話解決。**合作在指令之前就開始了。**

## 3.2 安裝本身與它建立了什麼

- **指令**：依 2026-10-20 的 README 是 `npx paperclipai@latest onboard --yes`，請從 README 複製當下版本。`--yes` 接受預設、不問問題——**接受預設的旗標就是替你回答了問題，答案是專案的，不是客戶的。**
- **建立了什麼**：一個本機 instance（實例），含自己的設定與資料、內嵌 PostgreSQL 資料庫、本機伺服器與網頁介面，以及存放公司、代理、任務與紀錄的地方；根目錄預設 `~/.paperclip/instances/default`。重跑 onboarding 會保留既有設定，另有 configure 指令事後修改。
- **要對客戶說的那句話：安裝讓公司成為可能，不讓公司受治理。** 官方 quickstart 的路徑是建公司、雇 CEO、看心跳，沒有任何要你設預算的步驟，卻另外警告代理會花錢、建議啟用心跳前先設預算；成本指南也說 App 內設定流程不會設預算政策。
- **也不設定模型存取**：CEO agent 要連本機 coding agent（如 Claude Code、Codex）或 API key，憑證自備。跳過這步，安裝看似成功，第一次心跳什麼都不會產出。
- **時間估計**：乾淨機器、熟手大約幾分鐘，加三到十分鐘準備 runtime 與憑證——不是給客戶的數字。客戶機器排半天，大多花在環境。誠實估計有兩個數字（順利幾分鐘、困難幾小時），跑完檢查前不知道是哪個；把檢查當成合作的一部分報價。
- **版本節奏**：10-20 讀取的 changelog 最新版 v2026.1012.0（10/12），前兩版 10/5、10/1。10/12 版要求升級或回滾前停掉所有舊伺服器並清掉遺留鎖定資料夾——更新客戶公司前讀 release notes 是專業，不是禮貌。

## 3.3 第一家公司：使命、名稱與 CEO

company 是一切的容器（代理、目標、任務、紀錄、預算），mission 在 goal chain 最頂端，每個任務都要能追溯回這句話，所以使命是每件工作繼承的指令，不是品牌口號。

- **最常見錯誤：把使命寫成願景。** 「革新小企業運用 AI 的方式」沒有產出、受眾、限度，代理只能猜，猜測的代理在排程上就是花錢做沒人要的事。有效寫法例如「每週五 9 點前，根據共用資料夾的專案筆記，替 10 位現有客戶各產出狀態報告，交客戶經理審查後寄出」——陌生人也能判斷做完沒有。
- **使命範本**：「在［截止或頻率］前，為［受眾］產出［產出物］，資料來源是［來源］，由［指名審查者］使用前檢查。」最常見錯誤是漏掉審查者，等於宣告沒人會看。
- **名稱**：測試公司看得出是測試，客戶公司看得出客戶與職能；一打 instance 之後，「Test 2」就是錯誤來源。
- **CEO agent 是協調者**：讀使命與目標、提議如何拆任務、可提議雇其他代理；它向 board（董事會）報告，策略與新聘送 board 決定。官方 quickstart 的第一次執行就是 CEO 產出策略、送出核准，任務要等你核准才上看板——一個做了事又停下來問你的代理，正是客戶付錢想看的行為。
- **Adapter（轉接器）**：選你手上最簡單的——同機已登入的 coding agent，或供應商端設了上限的 key。10/12 版縮短了新公司與新聘的預設指示、改了預設權限；讓 CEO 跑之前先讀它被給了什麼。
- **第一次心跳**：heartbeat 是排程喚醒，代理檢查有沒有工作、行動、回報。看執行紀錄的三件事：做的事和使命成比例嗎？它怎麼描述計畫？花了多少（第 8 章量測的第一份證據）。**心跳沉默不代表壞了**，最常見是模型憑證缺失或代理軟體沒裝——看起來像成功的失敗。先查連線、再跑一次、寫下漏了哪步。

## 3.4 排錯，以及預設留下的缺口

**通用方法**：不要小幅改參數重跑同一指令，而是問哪一層壞了：runtime、套件下載、本機伺服器、模型連線。先跑內建診斷 `doctor`（2026-08-25 release notes 起），讀它的輸出而不是假設它的範圍。三種常見失敗：

1. **Runtime 太舊**：檢查版本、升級或用版本管理工具切換後重跑。「檢查 runtime 版本」放每份客戶清單第一行。
2. **套件下載回 not-found**：全域設了私有 registry 時，私有庫沒有這個套件。確認生效的 registry，這一次強制用公開 registry。先懷疑 registry，再懷疑套件。
3. **Port 被占用**：找出占用者停掉，或改設定換 port。在客戶共用機上可能是別人依賴的服務，停之前先問。

第四個非安裝錯誤：模型連線缺失。其他都過、心跳卻沉默，就看這裡。

多數人遇錯就上網搜、套第一個修法，有時是刪掉 instance 資料庫重來；有效做法是跑診斷、套該層的文件化修法、重設前先備份。測試機刪了無妨；跑了一週的客戶公司，刪掉就是摧毀你被付錢保管的紀錄。**沒有備份、沒有客戶同意，絕不在客戶機器上重設。** 排錯 log 從第一次安裝就保留，它是附錄 C 檢查清單的原料，也是可信的經驗證據。

### 更大的缺口：沒人問預算

依 10-20 文件：quickstart 警告代理會花錢，預算可設在公司、代理、專案三層，到上限會暫停，建議啟用心跳前設好；但文件路徑沒有任何一步要求你做。成本指南也記載沒有預設金額、App 內流程不設。10/12 版還把預算搬到介面別處、改由命令列或代理 API 設定——控制還在，位置會變。結論：**控制存在、文件建議、預設不強制**，所以一家公司可以連上付費模型、放上心跳，卻沒有任何人選定的上限。

兩個讓論點保持誠實的提醒：一、強制依賴「已記錄的花費」，回報延遲或進行中的工作會讓花費在暫停前超過上限——強控制，非完美控制；二、公開來源對公司成本看法不一，取決於模型與心跳頻率。能對客戶說的不是數字而是順序：**先設上限、試行量測、再報價。**

這個缺口連回第 2 章三種對話：對 Control 客戶它就是提案；對 Visibility 客戶它解釋了意外帳單；對 Capacity 客戶它說明倉促建好放著跑的職能可能花得比省得多。

現在就做：公司建好後、任何代理按排程跑之前，以供應商端上限為後盾，替 CEO agent 與公司各設一個刻意偏小的上限並寫下來。**沒有天花板，就不開心跳。**

## 本章行動清單

1. 在測試機安裝。先跑六行檢查並記錄，包括官方當天要求的 Node.js 版本與讀取日期。
2. 用 3.3 範本建公司，使命一句話，寫出產出、截止、來源、審查者。
3. 用最簡單的 adapter 連 CEO agent（供應商端已設上限），啟用心跳前先設偏小的上限，跑一次心跳。
4. 記錄：從第一行指令到儀表板花多久、每個卡點與修法、有沒有畫面問預算、CEO 第一次心跳做了什麼、有沒有停下來問你。
5. 保留這頁，它是合作檔案（engagement file）第一筆，排錯段落是附錄 C 的起點。

## 本章小結

- 合作在指令前開始：六行檢查，最常漏的是所有權。
- 一行指令建立完整自給的 instance，但 `--yes` 回答的是專案的預設答案。
- 安裝讓公司成為可能，不讓它受治理：不設模型存取、不設預算。
- 使命要可驗證；CEO agent 協調並把重大提議送 board；心跳沉默先查憑證。
- 排錯分層診斷，不備份不重設；沒有天花板，就不開心跳。
